# Limits

What ipswrun cannot run or do yet, beyond the short list in the [readme](readme.md#what-does-not-work), ranked by how much real-world code each limit blocks. "Fixable" means a fix keeps to the project's rules: no guessed success for unimplemented calls, nothing keyed to one build, no kext emulation, and no replacing Apple's libraries.

The biggest gap is that nothing starts Apple's daemons on demand, so most frameworks quietly lose the services they lean on.

This list was made by reading the code, and then checked by one [survey](#survey-of-a-releases-own-binaries) of a release's own binaries. The [last section](#suspicions-not-yet-tested) lists what most needs a run to confirm.

## Ranked limits

| # | Limit | What it blocks | Where in the code | Fixable? |
| --- | --- | --- | --- | --- |
| 1 | The release's daemons are started only where asked for, and of the ones nearly everything asks notifyd and logd run, and opendirectoryd does not: `--on-demand` starts the daemon or agent of a service when it is looked up ([below](#daemons-on-demand)), and without it a Mach service exists only if it is named with `--service`, `--agent` or `--daemon` | Frameworks silently lose opendirectoryd, distnoted, trustd, securityd, tccd and fontd; daemons that need other daemons | `emulator/launchd.go` (`onDemand`), `emulator/build.go` (`launcher`) | One daemon at a time: each needs what it asks of the kernel and of launchd |
| 2 | A thread takes a signal only as it comes back from the kernel, or when it faults: handlers are run ([below](#signals)), but no thread is ever taken off the CPU for one. The timers that count a process's own time on the CPU (`ITIMER_VIRTUAL`, `ITIMER_PROF`) cannot be started | A handler for a thread that spins without a system call (a `SIGALRM` timeout around a loop that computes), profilers, Mach exception ports | `emulator/signals.go` | Taking a thread off the CPU is limit 7 |
| 3 | Descriptor I/O beyond files, pipes and pairs of sockets: no socket but those of a `socketpair` of stream sockets ([below](#pairs-of-sockets); `socket` answers EACCES). Pipes are there ([below](#pipes)), and such pairs, with `select`, `poll`, libdispatch's sources and a kqueue of the guest's own ([below](#a-kqueue-of-the-guests-own)), and a file can always be read and written, to `select` and `poll` alike. Of a terminal or any other descriptor `select` finds nothing ready, a `poll` that would wait for one stops as unimplemented, and a kqueue's `EVFILT_READ` and `EVFILT_WRITE` never happen, nor do `EVFILT_VNODE` and signals there: a `kevent` that would wait for one of those stops as unimplemented | Unix-socket clients (syslog, mDNSResponder), any network code, descriptors sent over a socket, `dispatch_io` on a file, programs that watch files or read a terminal as it is typed at | `emulator/pipes.go`, `emulator/kqueue.go`, `emulator/kevent.go` | Sockets with names in the file system, yes. A real network is a policy call, since it breaks reproducibility |
| 4 | Accelerate's BLAS and LAPACK: every release's libBLAS runs `cblas_sgemm` and the like on Apple's matrix coprocessor (AMX), whatever chip the guest is told it has, and Unicorn has no AMX; the run stops at the first AMX instruction and names it | Linear algebra through Accelerate, and what is built on it (CoreML's and BNNS's CPU paths, likely vDSP's matrix calls) | `emulator/process.go` (`amx`, `interrupt`) | Yes, [below](#amx-emulation): emulate the coprocessor in the invalid-instruction hook |
| 5 | No hardware beyond the device tree: the I/O Registry holds the restore image's device tree and nothing a driver or the boot loader adds ([below](#the-io-registry)), and a search finds no service but the device itself | Serial number and platform UUID, NVRAM, power, HID, most of MobileGestalt (it answers the marketing name, and no product type) | `emulator/registry.go`, `emulator/iokit.go` | Partly: each further fact needs a source in the restore image |
| 6 | Shared file memory: `MAP_SHARED` of a real file is a private copy, and there is no `msync`. Protections are kept per region (`mmap`, `mprotect`, `mach_vm_protect`, the `mach_vm_map` trap, the shared cache's own) and a forbidden access faults, but memory from the MIG `vm_map` and `mach_vm_remap` is mapped with every protection | SQLite WAL `-shm` files shared by two connections or processes; anything that writes a mapped file | `emulator/bsd.go` (`sysMmap`), `emulator/mach.go` | Shared file mappings, yes, through the `shm_open` path |
| 7 | Threads take turns on one CPU, with no preemption, and `hw.ncpu` is 1 | Spin-waits without a system call hang; nothing runs in parallel, so compute-heavy guests are slow | `emulator/threads.go` | Hard: Unicorn does not resume reliably after a stop from outside a hook |
| 8 | The system volume is closed by default: only feature flags, `SystemVersion.plist`, ICU data, the Objective-C trampolines, the sandbox profiles and the programs in `/bin`, `/usr/bin` and the like can be read, and the directories (and the symbolic links among them) on the way to the shared cache's images, which dyld walks, listing only what leads there | Frameworks' `Resources` (Info.plist, `.strings`, `.car`), fonts and other `/System/Library` data: frameworks behave differently with no error | `emulator/build.go` (`DefaultSystem`) | Yes, it is a default; `--system` already opens more |
| 9 | Device and OS coverage: iPhones and iPads from the A12 only; no tvOS, watchOS, visionOS or bridgeOS; no macOS before 11 | iOS 14 to 16 on A9 to A11 devices; the other Apple platforms | `cmd/ipswrun` device tables | A9 to A11 (plain arm64 caches) and tvOS look reachable; watchOS is arm64_32; macOS before 11 has no arm64 code |
| 10 | Hosts: an Apple silicon Mac, or Linux on arm64 or x86-64 with glibc; guests have to be built on a Mac | Intel Macs, Windows, musl Linux, CI without a Mac | `emulator/artifact.go` (pinned libunicorn builds) | Intel Macs and musl need a libunicorn build to pin; building guests on Linux needs an SDK |
| 11 | What the system says of itself is left out where it isn't known for sure ([below](#sysctls-left-out)) | A guest that needs one of those sysctls gets ENOENT, as from a kernel without it | `emulator/bsd.go` (`sysctlValue`, `cpuFamilies`) | Yes, one value at a time, from a real device or the restore image |

## What to fix first

These three would unlock the most code for the least work, and each keeps to the rules above.

1. **opendirectoryd under `--on-demand`.** notifyd and logd run, the second on a data volume ([below](#the-data-volume)). opendirectoryd is what nearly every program looks up next, and it calls `reboot`; until it runs, `--on-demand '*'` does not get far, and is not the default. The profiles the kernel has by name are read from each release's kernelcache now ([below](#daemons-on-demand)); what it needs next is not a call to add but three things to decide or be given: the system volume open to a daemon, the data volume's directories with their own owners and modes, and `identitysvc` measured as root.
2. **The system volume, open by default** (limit 8). Of the 26 everyday commands that still differ or stop ([below](#everyday-tools)), three print the same once it is open (`--system /`: `iconv` to UTF-16, `shasum`, `units`), and four more with a data volume as well (`--data`: the three that use a here-document, whose shell wants `/tmp`, and `crc32`): 122 of the 141 with both, where 115 match as a run is started by default. So it is fewer than was thought, and the data volume matters as much. Whether to open it is a default, and a matter of how much of the image a run may fetch.
3. **Taking a thread off the CPU** (limit 7). Signals, their handlers, faults and timers are there, but a thread that spins takes no signal, and nothing else runs meanwhile.

## Stubs that answer success

The `trivial` map in `emulator/bsd.go` used to answer 0 for calls that did nothing. These now do what they say, or stop as unimplemented where they cannot:

| Call | Now |
| --- | --- |
| `chmod`, `fchmod`, `fchmodat`, `chown`, `lchown`, `fchown`, `fchownat` | Change the host file under the home or a mount. A file of the system volume is refused as a real one is: EPERM for the user, who does not own it, EROFS for root. A guest's executable and devices are EPERM. `chown` to the owner a file already has succeeds, and to another is EPERM for the user ([examples/owners.c](examples/owners.c), as natively). Root gives a file away, and the machine keeps whose it then is: a file is its maker's and of its directory's group, which `stat` and `getattrlist` say. A Mac's kernel also lets an owner give a file to another of its own groups; which groups a user is in is not kept, so that is EPERM too |
| `setxattr`, `getxattr`, `listxattr`, `removexattr` and their `f` forms | Kept in a table in the `Machine`, keyed by the host file, so they read back alike on macOS and Linux hosts and between guests; dropped with the file's last link. System files have none and take none |
| `utimes`, `futimes`, `setattrlist`, `fsetattrlist` | Set the host file's dates; `setattrlist` also owner, group and mode, and stops as unimplemented for any other attribute |
| `flock` | The host's `flock`, so guests sharing a mount lock each other, and so do host processes. A blocking lock waits like the other kinds of wait |
| `mprotect`, `vm_protect` | Tracked per region; a forbidden access faults (see limit 6). It costs 2–4% on the example guests |
| `setrlimit`, `getrlimit` | Start as launchd gives them (no core files; an 8 MB stack, less a guard page, of at most 64 MB; 256 descriptors), and change as the kernel allows: a soft limit no higher than the hard one, a hard one raised only by root. The descriptors' limit is kept to (EMFILE). RLIMIT_NPROC's real value depends on the device's memory and is not known, so it stays unlimited |
| `fsync`, `sync` | The host's, for host files and the standard descriptors (EINVAL for a pipe, as on a Mac); 0 for what is read from the system volume. `fsync` of shared memory or a kqueue stops as unimplemented |
| `umask` | Kept, from launchd's 022, and applied to the files and directories a guest creates in place of the host's own umask |
| `getpriority`, `setpriority` | The process's nice value; a user may raise it but not lower it again. Darwin's own kinds (`PRIO_DARWIN_THREAD` and the like) stop as unimplemented |
| `iopolicysys` | Kept and read back by scope and type. Setting a policy that would change what files show (access times, skipped modification times, ignored permissions) stops as unimplemented |
| `memorystatus_get_level` | 50, as `kern.memorystatus_level` and `host_statistics` say |
| `sigaction`, `sigprocmask`, `sigaltstack`, `setitimer` | See limit 2 |
| `kevent`, `kevent64` | See limit 3 |

The rest of what the `trivial` map answered 0 now has no handler, and stops the run: `memorystatus_control`, `proc_rlimit_control`, `thread_selfusage`, `kqueue_workloop_ctl` ([there since](#everyday-tools)), `audit_session_self`, `debug_syscall_reject_config`, `debug_syscall_reject`, `record_system_event`, `log_data`, `oslog_coproc_reg` and `oslog_coproc`. None of the example guests calls them on the releases tested. `objc_bp_assist_cfg_np`, which libobjc of iOS 16.0 calls as it starts, fails with ENOTSUP, as on a core without the hardware that assists Objective-C breakpoints.

Found since, and put right: `fcntl` answered 0 for every request it had no answer for. One it has none for now stops the run and names itself, and those the example guests make were measured on macOS 27.2.1 and answered ([examples/rangelocks.c](examples/rangelocks.c), the same natively and on iOS). SQLite takes locks on parts of every database it opens that are the open file's (`F_OFD_SETLK`, and `F_OFD_GETLK` to ask what stands against one): they are kept by the machine, held by the open file and so by its duplicates and a copy of the process, refused to another open of the file where one of the two is to write (EAGAIN), changed in kind by locking again, and given up with the last descriptor of the open file; a lock to write is refused a file opened only to read and one to read a file opened only to write (EBADF). It also asks how a file is protected (`F_GETPROTECTIONCLASS`: 3 for a file and a directory, EBADF for a pipe; that an iPhone's files have this class unless given another is what Apple documents and was not measured) and to keep it from being moved (`F_SETCONFINED`: EBADF to set, EPERM to clear, and `F_GETCONFINED` 0, as a user's process is told). dyld asks whether a library is signed (`F_CHECK_LV`: 0 for a program with a code signature from where it starts in its file; EPERM and "Trying to load an unsigned library" for a file that is none and for the start of one that holds several). The 141 everyday commands were then run again, and every one stopped: the shell asks that each script it reads not be kept in memory, and `cp` asks for room ahead of what it writes. Those were measured and answered ([examples/fileflags.c](examples/fileflags.c)): `F_NOCACHE` and `F_RDAHEAD`, which here are only said back by `F_GETFL` (0x40000 and 0x80000), there being no such memory, and which a pipe is refused (EBADF); `F_FULLFSYNC` and `F_BARRIERFSYNC`, which are the host's `fsync`; and `F_PREALLOCATE`, which says all the room asked for was had, from the end of a file open to write (EINVAL from anywhere else and for less than nothing, EBADF for what is not such a file), with none kept on the host, so that what `stat` says a file takes on the disk does not grow as a Mac's does. `ssh` lists its own descriptors to close them (`proc_pidinfo`'s PROC_PIDLISTFDS, [examples/openfds.c](examples/openfds.c), the same natively and on iOS): each with its number and its kind (a file or a directory 1, a socket 2, shared memory 3, a kqueue 5, a pipe 6), whole ones only, ENOMEM into room for less than one, EPERM of launchd's; asked with no room it says how much the table of them would take, 20 places more than the table has, which starts at 25, is 64 once a descriptor of that number or above is opened, doubles after, and does not shrink. The table is larger here than a Mac's as a program starts, dyld having opened the shared cache's files, which a Mac's kernel has mapped already; of a process that began with a descriptor above the first 25, and of another process's descriptors, it stops. Older dyld tells the kernel what it will read soon (`F_SPECULATIVE_READ`: 0 of a file, there being nothing to do about it here; EINVAL from before its start, for less than nothing and of a directory; EBADF of a pipe). Told how its file is protected, SQLite opens it as a Mac's does, with `guarded_open_dprotected_np`, which is an open here as `guarded_open_np` and `open_dprotected_np` are: the guard is not kept and the class is not enforced. Not there, and stopping: waiting for such a lock that another holds (`F_OFD_SETLKW`), a process's own locks (`F_SETLK`), such locks on what is no file of the home's or a mount's, and any other request. Measured and not followed: a request the kernel has none of is ENOTTY on a Mac, which is not said here, there being no telling a number the kernel lacks from one that is only not written. A team's own libraries, and what else the kernel's check of a library looks at besides its having a signature, were not measured.

Still to check against a real kernel: the map's constant errors (`necp_open` and `getaudit_addr`, `coalition_info` and `persona` answer ENOSYS, `socket` EACCES, `work_interval_ctl` and `crossarch_trap` ENOTSUP), which fail but perhaps not as a Mac does..

## `__mac_syscall`

The calls guests make are answered as a Mac's kernel answers a process that is not sandboxed, as [examples/macsyscall.c](examples/macsyscall.c) measures them (run natively on macOS 27.2.1, with the arguments the guests pass). How cfprefsd uses them was checked by running a re-signed copy of this Mac's own cfprefsd under lldb.

| Call | Answer |
| --- | --- |
| AMFI 90, `amfi_check_dyld_policy_self` | 0, with the flags 0x1df |
| Sandbox 2, a check, of any process (even one that is not there) | 0, with a result of 0, allowed, for the filter types the guests use (none, a path, 5, 6, 0x1c, 0x41, a descriptor), except a path that does not exist, whose result is 2. That 2 was measured on this Mac only. A descriptor (0xf0) is EBADF, and the result left as it was, if it is not open |
| Sandbox 4, a query of a process | ENOTSUP for its container (kind 0), ESRCH for kind 1; the buffer is not written |
| Sandbox 12, `sandbox_passthrough_access`, as CFPreferences calls it for a plist it opened | 0 for a regular file with the flags 0x2 and 0x100 or neither; EACCES for one with 0x1 and for a directory; EBADF for a descriptor that is not open |
| Sandbox 22, a profile the kernel has by name, and Sandbox 1, putting it on | 0 for a name that is in the release's own kernelcache, read when a guest first asks for a profile the release has no file for; ENOENT for any other, as on this Mac for cfprefsd's, notifyd's and logd's, and libsandbox then compiles the profile from its file. Put on, a profile confines nothing, as a compiled one does not ([below](#daemons-on-demand)) |
| Sandbox 0, applying a compiled profile | 0, and nothing is confined (below) |
| Sandbox 67, `sandbox_get_container_expected` (iOS 18 and later, as every process starts) | 0, with both words it is given set to 0: no container is expected |
| Quarantine 87, `_qtn_proc_apply_to_pid` | 0, nothing written |
| Quarantine 82 and 80, what a file is in quarantine by, asked by a descriptor (`cp`, `gzip`) or by a path (`tar`): {the file, &room, a buffer} | The file's attribute `com.apple.quarantine` after `q/`, and how long that is; ENOATTR for a file that has none, ERANGE with too little room, EINVAL for a pipe, and of a symbolic link the link itself is asked. [examples/copied.c](examples/copied.c) prints the same natively |

**A deliberate exception: a profile that is applied confines nothing.** cfprefsd enters its sandbox as it starts, and a real kernel would hold it to its profile from then on. Here applying the profile succeeds and changes nothing, whether it was compiled from a file (Sandbox 0) or is one the kernel has by name (Sandbox 1, of which only the name is read), and a process that has put one on is still told it is in no sandbox, so a guest can do whatever its profile forbids, and sandbox behaviour can't be studied with ipswrun. This was chosen over stopping, so that cfprefsd, and the prefs guest beside it, run.

Everything else stops as unimplemented: putting on by name a profile the kernel has none for, issuing or consuming a sandbox extension (Sandbox 5 and 6 on this Mac, whose token is the kernel's), and any other policy, call, filter type, flags, descriptor or process not measured.

A guest may read the sandbox profiles (`/System/Library/Sandbox/Profiles/` and `/usr/share/sandbox/`, among the defaults of `--system`), so cfprefsd compiles its own and applies it (Sandbox 0) as on a Mac. Without them a daemon's `sandbox_init` fails with "profile not found": cfprefsd then cannot synchronize on macOS 15 and later, and in the survey 56 programs said so as they started.

The answers were measured on a Mac; iOS guests get the same ones, which is not known to be what an iPhone's kernel answers.

## Preferences on iOS 16 and later

The prefs guest, run beside the release's own cfprefsd, prints `synchronized: 0` on every iOS release from 16.0 that was run (16.0, 18.0, 18.7.12, 26.0, 26.6.2, 27.0, 27.2.1): CoreFoundation never looks up `com.apple.cfprefsd.daemon`, so `CFPreferencesAppSynchronize` returns false, while what was set still reads back from the process itself. On iOS 14 and 15 it looks the daemon up (launchd's routine 804) and synchronizes. Why it doesn't is not known yet; it was so before the sandbox calls were answered.

## The I/O Registry

The registry is the device tree the restore image has for the `--device`, shown as the plane `IODeviceTree`, with the registry's root above it. It is read from the image when a guest first asks. [examples/registry.c](examples/registry.c) prints the same run natively on a Mac15,9 with macOS 27.2.1 as under ipswrun for that device and release ([native.txt](examples/expected/registry/native.txt)), and the release's own `ioreg -p IODeviceTree` prints the tree.

The image holds the tree as the boot loader is given it, not as the boot loader leaves it. What is left out, so as not to be invented:

- **A value the image marks as one for the boot loader to fill,** and **a value that is all zeros**, which is how the image holds the place of most of the others. Measured against that Mac's live registry, over the 42 entries `ioreg` shows of its tree: of the 505 unmarked values the image has, 312 are not zeros, and all but one of those are what the Mac has (the one, `pmap-io-ranges` of `/defaults`, is longer on the Mac); 189 are zeros, of which the Mac has 140 as they are and 49 filled in (`chip-id`, `board-id`, `firmware-version` and the like in `/chosen`). So a property that really is zero (`has-exclaves`) is not there to read either.
- **What only a running device has:** its serial number and platform UUID, everything in `/options` (the NVRAM, which is there as an entry with no properties), the entries the boot loader adds under `/chosen`, and the properties drivers add.
- **Classes, locations and identifiers.** An entry's class is its driver's, so only the device's own (`IOPlatformExpertDevice`, which the kernel itself makes of the tree) is answered; a search for that class finds it, and for any other class finds nothing. `io_object_get_class` of another entry, an entry's location, its registry ID and its path are not answered: the guest gets a send error, and the request is listed when the run fails or under `--missing`. A path with a location in it (`cpu0@0`) stops as unimplemented.
- **The properties of the root, and of an entry the kernel keeps to itself** (`kernel-only`, such as `/chosen/memory-map`), which a Mac shows emptied: they stop as unimplemented.
- **The order of the entries under one.** They come in the tree's order. A Mac's kernel has the device's in another (`chosen`, `aliases`, `memory`, `options`, `cpus`, where the tree has `chosen`, `options`, `cpus`, `aliases`, `memory`).
- **Every plane but the tree's.** Among the services there is the root and the device and nothing under it, as no driver is here: `IOService:/IOResources/AppleKeyStore`, which is there on every device, is not. A search or walk that would leave the device tree's plane from any other entry stops as unimplemented.

To be told of services arriving (`io_service_add_notification_bin`) is to be handed those already there, and no message after: the services of a machine here are all it will have.

Not known to hold on an iPhone: the rule for zeros and the device's name (the first of its `compatible` strings) were measured on a Mac. The iOS runs were read, not compared with a device.

## Survey of a release's own binaries

Every Mach-O executable in `/bin`, `/sbin`, `/usr/bin`, `/usr/sbin` and `/usr/libexec` of macOS 27.2.1 (26B131), 1,293 of them, was run once with no arguments under `--missing` and a 60-second limit, before and after the registry, the sandbox profiles and the calls below were added. With no arguments most only start up, or print their usage (344 did), so this counts what a program needs to start, not to do its work. It was not run on iOS or on another release.

| | Before | After |
| --- | --- | --- |
| Made no call that is not implemented | 1,098 | 1,134 |
| Made at least one | 195 | 157 |
| Sent the registry or IOKit a request nothing answered | 48 | 2 (`ioreg`, asking for classes, and one asking for a driver's connection) |
| Said its sandbox profile was not found | 56 | 1 |
| Ran until it was a service waiting for a client, which is how a daemon run alone ends | 45 | 63 |
| Ended with a crash of its own (an abort or a trap) | 71 | 68 |

After everything below was added, the survey was run once more: 1,172 make no call that is not implemented, and 119 make at least one, of which 8 only sent a message to no port at all (a lookup of theirs had found nothing), which a Mac's kernel refuses as it is refused here and is no longer listed. What is still asked for by more than five: launchd's event streams (routine 401, by 15 programs, for a stream such as `com.apple.remoted.service`; what launchd answers is its own protocol and was not measured) and the properties of the registry's root (10, the kext tools). Nothing else is asked for by more than five programs that only start: what is left of the ranked list (signals, `fork`, sockets, the daemons) shows in programs that do their work, which this survey does not run.

In the first two runs, what was asked for most that was not there, by programs asking: `getrusage` (21; [there now](#what-a-process-has-used)), launchd's routine in message 1073742225 (16), the kqueue filter for user events (13), `pipe` (9), the properties of the registry's root (9, the kext tools), `kqueue_workloop_ctl`, `memorystatus_control` and `mach_port_get_attributes` (5 each; the last is [there now](#a-ports-status)).

One run of it filled the disk: `/usr/bin/yes` writes without end, and a guest's output was kept until it ended, with no limit on how much (27 GB in its 60 seconds). Since then the output of a run against one release is passed on as it is written, and where it has to be kept (several releases, whose outputs are compared, and the guests started beside the first) a guest that writes more than 64 MB stops the run and says so.

What it did not confirm from the ranked list: pipes (9 programs), and `fork`, `execve` and `posix_spawn` (6 between them), which a program asked for nothing does not reach.

Added after it, each answered as macOS 27.2.1 answers a process that is not root: `getlogin` (the user's name, with the zeros after it for as much of the kernel's 255 bytes as there is room for; it stops as unimplemented for a daemon and on iOS, where the name of launchd's own session is not known), `getdtablesize` (the soft limit on descriptors; unimplemented above 10240, where `kern.maxfilesperproc`, which is not known, could be the lower), and `setuid`, `seteuid`, `setgid` and `setegid` (0 to become what the process already is, EPERM for anything else; root becoming another user or group stops as unimplemented, as a process here has one of each).

Left as they were, still stopping or listed by name:

- **`confstr(_CS_DARWIN_USER_CACHE_DIR)` and the like**, which 15 programs end on. The directory is made by the release's `dirhelper`, and that was followed as far as it goes. Started by hand (`--daemon com.apple.bsd.dirhelper=system:/usr/libexec/dirhelper`) it checks in and takes the request. It needs `/var/folders`, which is on a device's data volume and so in no restore image (`--mount /var/folders=<dir>` gives one). It then makes `/var/folders/zz` and marks it with a call of the sandbox's (number 261 on macOS 27.2.1, given the directory and the word `folders`), which on a Mac leaves the directory with the extended attribute `com.apple.rootless` set to `folders`. That call is one of System Integrity Protection's: its number is a release's own, and what it answers can only be measured by a process that is root and entitled by Apple, so it stays unimplemented and dirhelper gives up there. Starting dirhelper when it is looked up would not change that.

## Everyday tools

The survey above starts each program and no more. So 76 commands that do a tool's work (`mkdir -p`, `cp -R`, `mv`, `ln`, `rm -r`, `find`, `grep`, `sed`, `awk`, `sort | uniq`, `tar`, `gzip`, `zip`, `plutil`, `sqlite3`, `zsh -c` and the like) were each run by the release's own `/bin/sh` on macOS 27.2.1 and by this Mac's, in a new directory, and what they printed compared. At first none got through: the directory was made with `mkdir -p`, which stopped. After what follows, 64 print the same.

What was missing, each measured natively and now there:

- **The stat calls that also tell of a file's security** (`stat64_extended`, `lstat64_extended`, `fstat64_extended`), which `mkdir -p`, `ls -l` and `cp` make. No file here has an access control list, and of one that has none a Mac's kernel writes 44 bytes that say so.
- **Whether a file is in quarantine** (Quarantine 80 and 82, [above](#__mac_syscall)), which `cp`, `tar` and `gzip` ask of what they copy.
- **Symbolic and hard links** (`symlink`, `symlinkat`, `link`, `linkat`), a file's count of names, `O_NOFOLLOW` of a link (ELOOP), and `unlinkat` as `rm -r` calls it (the flag 0x100 for a directory): [examples/links.c](examples/links.c). ## Daemons on demand

`--on-demand <service>` has launchd start the build's own provider of a Mach service when the service is first looked up and no guest provides it: the daemon or agent whose launchd plist (in `/System/Library/LaunchDaemons` or `LaunchAgents`) names the service, with the program, arguments and environment the plist gives beside the guest's own environment, as root or as the user the plist names (by the build's own `/etc/passwd`), or for an agent as the guests' user. A pattern names several services, and `*` every one. The service is there at once, as launchd has it, and what is sent to it waits for the daemon to check in. Reading the plists, some 900 of them on macOS 27.2.1, takes about 2.6 seconds and 14 MB of the image, once a run, when the first service is looked for.

`--on-demand 'com.apple.cfprefsd.*'` does for the `prefs` guest what `--agent` and `--daemon` with cfprefsd's path and its role did by hand, with the same output on every macOS release in the matrix, which now runs it that way. iOS has no plist for cfprefsd as an agent, so there both are still started by hand.

`--on-demand com.apple.system.notification_center` starts the release's own notifyd, and [examples/notify.c](examples/notify.c) prints the same with it as natively on macOS 27.2.1 ([native.txt](examples/expected/notify/native.txt)) on every macOS and iOS release in the matrix: a name's state set and read, posts checked for, a block and a Mach port told of a post, a registration suspended and resumed, and tokens cancelled. What notifyd needed was launchd's part in a daemon that publishes events (`xpc_event_publisher`): it asks for the events of its stream `com.apple.notifyd.matching` (routine 403, answered with none, as before) and then sends routine 406 with a port to be answered on. libxpc's own code shows what that is: it goes on without waiting, and an answer means that what subscribes to the stream has changed, after which it asks for the events again and sends 406 again. Nothing subscribes here, so launchd keeps the right to answer and never does. Before, the message was refused, which notifyd takes as a bug of its own and traps on.

It is not the default, and `'*'` does not get far: a daemon that makes a call that is not implemented stops the run and names it, as any guest does, and two that nearly every program looks up each do, on macOS 27.2.1:

- **logd** (`com.apple.logd`) runs, given a data volume to keep its files on ([below](#the-data-volume)) and the notifyd it asks: `--data <dir> --on-demand 'com.apple.logd*' --on-demand com.apple.system.notification_center`. [examples/oslog.c](examples/oslog.c) prints the same with it as natively on every macOS release in the matrix, and on macOS 15.6.1 and 27.2.1 what the guest logged was found in the `tracev3` file logd wrote. Three things it asks are not there, each named by `--missing`, and it goes on without them: two requests of the host's port (messages 225 and 425, the second for the kernel's extensions, which it says on its standard error it could not read) and a kqueue's watch of a file (`EVFILT_VNODE`). What it needed on the way: `fchmodat` and `fchownat`, a file's owner kept, `kern.boottime`, `kern.bootsessionuuid`, and the trap for exclaves (88), each [below](#what-logd-asked-for). Not on iOS, which has no data volume here.
- **opendirectoryd** (`com.apple.system.opendirectoryd.libinfo`) gives up as it starts: its `sandbox_init` fails with "profile not found", and it then asks the kernel to panic (`reboot` with RB_PANIC, which is not implemented and stops the run). Its profile is no file of the release's: a Mac's kernel has it by name, built into its sandbox extension (Sandbox 22 answers 0 for `com.apple.opendirectoryd` on macOS 27.2.1, and ENOENT for the seven other daemons tried). Which names a release's kernel has is in its kernelcache, and was looked for there: the names are in it, but so are the same names in other lists (the daemons whose profiles the kernel does not have among them), so telling them apart means reading the sandbox extension's own table of profiles, whose layout is each release's. Left there: without opendirectoryd a program's users and groups come from `/etc/passwd`, as before. **Measured since, and what it leads to:** every one of the six everyday commands that differ for want of a daemon (`defaults`, `pgrep`, `nohup`, `osascript`, `mdfind`, `plutil`) was run with `--on-demand '*'` and a data volume, and none got as far as its own work: `/bin/sh` itself asks opendirectoryd who the user is as it starts, and waits for good on a daemon that has given up. So this is what stands before all of them. A Mac's kernel was then asked (Sandbox 22) of every name it could have: of the 610 profiles that are files of the release (`/System/Library/Sandbox/Profiles`, `/usr/share/sandbox`) it has none, and of the 63,433 strings of its own kernelcache that could be a name it has 14: `com.apple.corebrightnessd`, `com.apple.dext`, `com.apple.endpointsecurity.endpointsecurityd`, `com.apple.oahd`, `com.apple.oahd-helper`, `com.apple.oahd-root-helper`, `com.apple.opendirectoryd`, `com.apple.sandboxd`, `com.openssh.sshd`, `no-internet`, `no-network`, `no-write`, `no-write-except-temporary` and `pure-computation`. Those 14 are where the first look could not tell them apart: one table in the kernelcache of macOS 27.2.1, which begins with the number 0x8000, says how many profiles there are, and has a record of one size for each, whose first number is where its name is among the strings that follow the table. Read so, it gives those 14 names and no other. **It is read from each release's own kernelcache now** (a member of the restore image of some 34 MB, fetched and unpacked when a guest first asks for a profile by a name the release has no file for, which takes a few seconds). Where the table is and how long its parts are is found from the table itself: it is looked for in the sandbox extension, where the kernelcache names its parts, and is taken for the table only if every profile's record leads to a name, no two to the same, and the rest of each record is numbers of the table's own nodes (without that last, two runs of three strings were taken for it on macOS 11.6). The three newest releases have a second such table after it, of profiles for the extension's own tests (`autobox-tests-allow` and the like), which the kernel of macOS 27.2.1 was measured not to give by name: the first is taken, on that one measurement. On macOS 27.2.1 that gives the 14 names the kernel was measured to have; on macOS 11.6 to 27.0 it gives the same 14, and on 11.0.1 twelve of them (not opendirectoryd's, which is a file there), which no kernel was there to check. What was read is kept between runs where there is a cache directory (`--cache`): the names, in a small file for that kernelcache (its file in the restore image, by name, size and checksum) and for the way they were read, so that a later run that asks does not fetch or unpack the kernelcache at all (about a second saved, measured on macOS 27.2.1). A kernelcache that could not be read is not kept, and is read again and said again by each run that asks; `--prune-cache` removes what was kept. On the six iOS releases no table is found, an iPhone's being made otherwise, and a guest there that asks for a profile by a name with no file stops the run as unimplemented, where it was told there was none. [examples/profiles.c](examples/profiles.c) prints the same natively. With its profile opendirectoryd gets further and gives up again, and what it says as it asks the kernel to panic is now said with the stop (`reboot` with RB_PANIC and a message). Three things stand between it and an answer, found one after another: (1) it wants `/System/Library/OpenDirectory`, which the closed system volume keeps from it (`--system /System/` and the like open it); (2) with that, it says "Failed loading node configuration for /Local, directory named \"Default\" wasn't found or didn't contain users/groups": the directory is there, on the data volume, but as the user's and for all to read, where a Mac's is root's and its own alone, which is the modes and owners the image's reader does not give ([above](#everyday-tools)); told once, and not kept, that `/private/var/db/dslocal` is root's and mode 700, it goes on; (3) to `identitysvc` (system call 293), by which it makes itself the kernel's resolver of users and groups, which only root may call on a Mac and so could not be measured here. `configd`, which it also asks for, exits as it starts. None of the three is a missing call that can be measured and added: the first is a default to choose, the second needs the image's reader changed, the third needs a Mac's root.

A daemon whose plist names a user the build's password file does not have, or whose program is not on the system volume, is not started, and its service is not there. The other keys of a plist (`LaunchEvents`, `Sockets`, `KeepAlive`, the session an agent is limited to, `RunAtLoad`) are not acted on: a daemon is started for a lookup of one of its Mach services and for nothing else.

### What logd asked for

- **A file's owner** is kept, as above: before, `chown` by root stopped as unimplemented, since every file was the guests' user's.
- **`kern.boottime`** is when the machine's own counter was at nothing, which is what the guests' time since boot counts from. A Mac's kernel says a time some seconds after that (9.6 on the Mac measured), those it took to come up.
- **`kern.bootsessionuuid`** names the one boot there is: a UUID of the random kind in capitals, the same on every run, as the machine's own UUID and its entropy are.
- **The trap for exclaves** (88, `_exclaves_ctl_trap`), the world that the A18 and the M4 and later keep apart from the kernel. A Mac with an M3 was measured to answer every request, whatever it is given, with "not supported" (46), and so does every chip here from before those. For a chip that has them, or one not known, it stops as unimplemented. [examples/boot.c](examples/boot.c) prints the same natively as under ipswrun for these three.

### The data volume

What logd, dirhelper, opendirectoryd and cfprefsd's daemon keep is on a device's data volume, beside the sealed one the system is on. `--data <dir>` gives the machine one, in a directory of the host's, as a macOS release itself describes it:

- **Which paths are the volume's** is in the release's `/usr/share/firmlinks`: `/Library`, `/private`, `/Users`, `/usr/local` and 15 more on macOS 27.2.1. Each whose directory a new volume has becomes a mount into the host directory. The home and any `--mount` are still their own.
- **What a newly installed Mac's has in it** is the release's `/System/Library/Templates/Data`, some 12,000 files in 5,800 directories on macOS 27.2.1. A directory of the volume is given what the template has in it (its directories, its symbolic links, and its files with their permission bits) the first time a path leads into it, and never again: what a guest then makes, changes or removes stays so, in the next run too, as the host directory and the list of what was filled (`<dir>/filled`) are kept.

[examples/datavolume.c](examples/datavolume.c) prints the same with it as natively on every macOS release in the matrix. With it came that `/etc`, `/tmp` and `/var` are the symbolic links into `/private` that every release has (they were directories, and `/var` and `/tmp` did not lead to `/private` at all), so `realpath("/var/db")` is `/private/var/db`.

What is not as on a Mac:

- **A new Mac's time zone.** The template's `/etc/localtime` is a link to `US/Pacific`, so with a data volume the time is Pacific time where without one it is GMT. That is what a new Mac says before anyone sets it up.
- **Whose the template's files are, and the modes of its directories,** are not read from the image: the files are the guests' user's, as everything is, and the directories 755.
- **The files of a directory are copied when it is first entered,** read or not. A directory whose files come to more than 64 MB stops the run and says so; none that was entered here does.
- **A symbolic link that leads out of its mount** (an absolute one, as `/etc/localtime` is) can be read as a link but not followed: opening it is EACCES.
- **iOS** has no `firmlinks` and no template: its data volume is `/private/var`, and what a new one has was not looked for. `--data` says so and stops.
- **It is not the default.** Without `--data` there is no data volume, as before.

## Starting programs

A process makes a copy of itself with `fork`, and starts another with `posix_spawn`: a program of the build's, of the home or a mount, or the guest's own, as a process of its own on the machine, with its parent's descriptors (a pipe's ends among them, which is how a parent reads what its child writes), the file actions and the flags a Mac's kernel was measured to take, and the directory of the thread that started it. `execve` puts a program in the place of the one that calls it, and `wait4` tells a parent how a child ended. [examples/spawn.c](examples/spawn.c) prints the same natively on macOS 27.2.1 as under ipswrun ([native.txt](examples/expected/spawn/native.txt)), and so does [examples/shell.m](examples/shell.m), which runs the release's own `/bin/sh` through `system()` and `popen()` and its `/bin/echo` through `NSTask`, on every macOS release in the matrix.

`fork` gives the copy its parent's memory, descriptors (a pipe's ends and a file's place are the same in both; a kqueue is not the copy's), handlers, mask and directory, and the one thread that called, and each is told which it is by what `fork` answers. [examples/fork.c](examples/fork.c) prints the same natively as under ipswrun ([native.txt](examples/expected/fork/native.txt)) on every macOS and iOS release in the matrix: a copy that changes its memory, writes to a pipe and a file, takes a signal with its parent's handler, becomes another program, aborts, is ended by a signal, and exits through `exit`. That is what a shell needs for a command that is not built into it, so the release's `/bin/sh` runs tools, pipelines, `$(...)`, subshells and jobs it waits for (`shell.m` has one of each). A process's number is not given twice in a run.

For starting programs:

- **A kqueue is told of a process ending** (`EVFILT_PROC` with `NOTE_EXIT`, which is how `NSTask` and a dispatch source learn of it), with its status if asked, and refuses to watch one that has ended already, as a Mac's kernel was measured to.
- **A descriptor can be marked not to be a started program's** (`FD_CLOEXEC`, `O_CLOEXEC`, `POSIX_SPAWN_CLOEXEC_DEFAULT`), which was ignored before.
- **A thread can have a working directory of its own** (`__pthread_chdir`, `__pthread_fchdir`), which is how Foundation before macOS 26 starts a program somewhere else.
- **A port can be in several port sets**, and a message to it is for whichever is received from first ([examples/portsets.c](examples/portsets.c)). It could be in one, and a second took it from the first, which left a run loop deaf to a wakeup.
- **The programs of the build can be seen** (`/bin`, `/sbin`, `/usr/bin`, `/usr/sbin`, `/usr/libexec`, among the defaults of `--system`), as a program that starts one looks for it first. Any of them can be started, whatever a guest may read.
- **`getppid`, `getpgrp` and `getpgid`** answer for the process, where they answered 1 and the caller's own pid.

What is not there, or not as a Mac has it:

- **`vfork`,** which stops as unimplemented.
- **The ports a task registers for its copies.** `fork` in libSystem sends `mach_ports_register` and `mach_ports_lookup` to the task's port, and neither is answered: the message is refused as one to a port that is gone, as any message nothing implements is, and libSystem goes on. `--missing` lists both. A copy starts with launchd's port and no other right; one whose parent registered ports would not find them.
- **A copy's memory is copied when it is made,** every page its parent has touched, where a Mac's kernel copies a page only when one of the two writes to it. It was first copied a page at a time, which took 11 seconds a `fork` (the engine is slow over each mapping it is given); in runs of pages it takes a fraction of a second, and more for a parent that has touched more.
- **A script** is handed to the program its first line names (`#!`), as a Mac's kernel hands it: that program's path, the words after it on the line, the script's path, and the script's arguments ([examples/script.c](examples/script.c), as natively). A script whose program is itself a script stops as unimplemented. Any other file that is no program is ENOEXEC.
- **What a process hands on** is one list for a copy (`fork`), a program it starts (`posix_spawn`) and the program it becomes (`execve`): who it is, where its output goes, its umask, its limits (`setrlimit`), its priority and its I/O policies. A started or replaced program used to get none of the last three, so `ulimit -n 64; tool` in a shell gave the tool the default. Beside those, as before: a copy keeps its handlers and no timer; a started program keeps what is ignored and blocked, and has no timer; the program a process becomes keeps what is ignored and blocked and its timer. [examples/inherit.c](examples/inherit.c) prints the same natively. A thread's own I/O policy is handed to a copy only, and whether a started program should have it was not measured.
- **A session or a group of its own.** `setsid` takes a process to a session and a group of its own, as one that makes itself a daemon asks; the first of a group, as one launchd started is, stays (EPERM). `setpgid` moves the caller, or a copy of it that is still the program it was, into a group of its own or another of its session: a child that was started as or has become another program is EACCES, any other process ESRCH, one that leads its session EPERM, and a group there is not EPERM. A process whose parent has ended says launchd is its parent (`getppid`). A signal that is blocked and waits goes with a process to the program it becomes. [examples/sessions.c](examples/sessions.c) prints the same natively. A session has no terminal here, and `POSIX_SPAWN_SETSID` still stops as unimplemented. `posix_spawn` into a group by its number took any number; it now asks what `setpgid` does, as a Mac's was then measured to ([examples/spawngroup.c](examples/spawngroup.c), the same natively and on iOS): a group that no process of the session is in, launchd's among them, is EPERM, one below zero EINVAL, and nothing is started. `proc_pidinfo` now says the same parent and group as `getppid` and `getpgrp`, where it said launchd and the process's own pid for every process.
- **Found beside it, and since put right:** what `fsgetpath` knew of a file was each process's own, so a file's number that one process learned was unknown to a program it started. It is the machine's now, and any process's to ask (the same guest). A file that no guest has looked at is still not found by its number, where a Mac's kernel finds any file there is.
- **What was not measured stops as unimplemented:** the flags of `posix_spawn` other than those for the signals, the process group and the descriptors to close (starting suspended, `POSIX_SPAWN_SETEXEC`, a new session), its port actions, `wait4` for a process group or with options other than `WNOHANG` and `WUNTRACED`, `execve` by a process with more than one thread, and `getrusage` of the children of a process that has started some.
- **The memory of a process that has ended is kept until the run ends.** Closing its engine while others run took memory of theirs with it (a fault inside Unicorn on the next stretch of emulation), so the engines are closed together at the end.
- **`/private/var/select/sh`,** which says which shell `/bin/sh` is, is on a device's data volume: the release's `sh` says on its standard error that it cannot open it, and runs `bash`, as it does on a Mac where the link is not there.

## What a process has used

`getrusage` answers with the machine's own account of the process, as its clock is its own: the time its threads had the emulated CPU, as the user and in the kernel (a system call, a trap or a fault), by the machine's clock, which stands still while the host fetches; the most pages it has had, as its memory; the faults that brought pages in, a major one being one that read a file of the build; and how often a thread of its gave up the CPU to wait. Twenty-one of the release's programs asked, the shells among them. What a Mac's kernel was measured to keep at zero whatever a process does is zero (the sizes of text, data and stack, swaps, block input and output, messages), and so are signals, as none is delivered, and the times a thread was made to give up the CPU, as none is. Of its children it is what those it has waited for used, and theirs, and nothing of one not yet waited for: the times and counts together, and of memory the most any one had, as a Mac's kernel was measured to add them ([examples/everyday.c](examples/everyday.c)).

The numbers are not a Mac's, and cannot be: the emulated CPU is many times slower, and brings pages in sixteen at a time. [examples/usage.c](examples/usage.c) prints what holds of them on any machine (work adds to the time, waiting does not, nothing goes down) and prints the same natively as under ipswrun. The times in `task_info` are answered (see the everyday tools); `thread_selfusage`, `proc_pid_rusage` and the times in `thread_info` are still not.

## Pipes

`pipe` makes one, and its two ends are read, written, duplicated and closed as on a Mac: [examples/pipes.c](examples/pipes.c) prints the same natively on macOS 27.2.1 as under ipswrun ([native.txt](examples/expected/pipes/native.txt)). A pipe holds 16384 bytes, and 65536 once more than that is asked of it; a write of 512 bytes or fewer goes in whole or not at all; a reader with nothing to read waits for a writer, and a writer with no room for a reader, each until the other has done its part or its end is closed. `select` says which ends are ready, and waits for one to be. `fstat`, `fcntl` (the flags, with `O_NONBLOCK`, and `F_SETNOSIGPIPE`) and `ioctl` (`FIONREAD`, `FIONBIO`) answer as measured. With the release's own `/bin/zsh`, `-c 'echo hi'` now runs, and a command that is not built into the shell stops at `fork`.

libdispatch watches a descriptor through its work queue's kqueue, with the filters `EVFILT_READ` and `EVFILT_WRITE`, and for a pipe these now happen: an event when there is something to read, with how much, or room to write, with how much, and one with `EV_EOF` when the other end has gone. [examples/pipeevents.c](examples/pipeevents.c) prints the same natively as under ipswrun ([native.txt](examples/expected/pipeevents/native.txt)): a source for reading, one for writing, `dispatch_read` and `dispatch_write`, and a `dispatch_io` channel. `NSPipe` with a `readabilityHandler` and `readDataToEndOfFile` was run once and did the same as on the Mac.

What is not there, or not as a Mac has it:

- **A write with nobody to read it** is EPIPE, after SIGPIPE unless the descriptor asked for none: the signal ends the process, or its handler is run, or it is ignored.
- **The number `fstat` gives each end** is made up by a Mac's kernel, differently every time, and is another made-up number here.
- **A pipe is one process's.** A started program or a copy has its parent's descriptors (`fork`, `posix_spawn`), but none is sent in a message.
- **`O_ASYNC`, and the size of a pipe on a system short of memory for pipes**, where a Mac's kernel gives them less. What a kqueue is told of the end of a pipe that is not the one read, or written, was not measured, and stops as unimplemented.

## Pairs of sockets

`socketpair` makes two connected stream sockets of the local domain, and what is sent into one is received from the other, both ways: [examples/socketpair.c](examples/socketpair.c) prints the same natively on macOS 27.2.1 as under ipswrun ([native.txt](examples/expected/socketpair/native.txt)) on every macOS and iOS release in the matrix. What was measured, and is as on a Mac:

- **How much waits, and when a sender does.** 8192 bytes wait to be received at most. A send that fits goes in whole; one that does not goes in as far as there is room, but only where there is room for 2048 bytes (`SO_SNDLOWAT`), and otherwise waits, or is EAGAIN for one that does not wait. That is also when `select`, `poll` and a kqueue say a socket can be written.
- **`read`, `write`, `readv`, `writev`, `send`, `recv`, `sendto` and `recvfrom`,** with `MSG_PEEK`, `MSG_DONTWAIT`, `MSG_WAITALL` and `MSG_NOSIGNAL`. `readv` was not there at all before, for any descriptor.
- **The other going, or saying it will send no more** (`shutdown` with `SHUT_WR`): the end is read after what was sent, a send is EPIPE with SIGPIPE (unless `SO_NOSIGPIPE`, `F_SETNOSIGPIPE` or `MSG_NOSIGNAL` asked for none), `poll` says POLLHUP, a kqueue EV_EOF, and `fstat` takes away the mode's read or write bits. A second `shutdown` of the same way is ENOTCONN, and a socket that can do neither takes no `setsockopt` and has no `getpeername` (EINVAL).
- **`getsockopt`** for the type, the sizes, the low-water marks, the error, how much waits (`SO_NREAD`; `SO_NWRITE` is always 0) and `SO_NOSIGPIPE`; `getsockname` and `getpeername`, which are 16 bytes that name nothing; `FIONREAD` and `FIONBIO`; `fcntl`'s flags.
- **libdispatch's read and write sources and `dispatch_io`** on a socket, a kqueue of the guest's own, a second descriptor (`dup`), and a copy of the process at the other end (`fork`).

What is not there stops as unimplemented and names itself:

- **To receive no more** (`shutdown` with `SHUT_RD` or `SHUT_RDWR`, where it would not be ENOTCONN). On a Mac what is then sent to the socket is taken and lost, `poll` no longer says the sender can write, and a sender of more than fits waits for good; how much is taken before that was not measured.
- **Pairs of datagram sockets.** How much one holds depends on how the kernel keeps each datagram (32 one-byte datagrams fill one, or 4000 bytes in four), which is its memory's own arithmetic.
- **`sendmsg` and `recvmsg`,** and with them descriptors sent over a socket; `recvfrom` asking whom it is from, `sendto` with an address, a send of nothing, `MSG_WAITALL` on a socket that does not wait (which waits all the same on a Mac), any option of `getsockopt` and `setsockopt` not named above, and O_ASYNC.
- **Any other socket:** `socket` answers EACCES as before, so there is no `bind`, `connect` or `listen`, and no network. A `socketpair` of the Internet's is EOPNOTSUPP, as on a Mac.

## Signals

A signal ends the process it is sent to, does nothing, or has the process's handler for it run: by what the process has said of it (a handler, or `SIG_IGN`, which a program it starts inherits) or by what the signal does unasked, which for most is to end the process and for a few (`SIGCHLD`, `SIGURG`, `SIGWINCH` and the like) is nothing. `kill` sends one to a process, `pthread_kill` to a thread of the caller's own, which is how `abort` and `raise` send theirs, a pipe sends SIGPIPE to a writer nobody reads, and a child that ends sends its parent SIGCHLD. A parent is told by `wait4`, and a kqueue by its process filter, of the signal that ended a child. A guest that a signal ends makes ipswrun exit with 128 and the signal's number, as a shell reports it (134 for `abort`, where it was 70), and say which on its standard error.

A handler is run as a Mac's kernel runs it. What the thread was doing goes on its stack, or on the one it set aside (`sigaltstack`, `SA_ONSTACK`), as what the handler is told (`siginfo_t`), the context it interrupted (`ucontext_t`) and the machine's state in it, every register with the vector ones; the thread goes on in libc's trampoline, which calls the handler; and `sigreturn` takes the frame back, changed or not. While it runs its signal is blocked, with those the handler asked for, unless it said otherwise (`SA_NODEFER`); a signal that is blocked waits, and is taken when it no longer is; `SA_RESETHAND` is for once. A call that waits (a read of a pipe, `wait4`, `select`, `kevent`, a sleep, `sigsuspend`) is interrupted, and fails as interrupted or is made again (`SA_RESTART`), as a Mac's does. [examples/signals.c](examples/signals.c) and [examples/handlers.c](examples/handlers.c) print the same natively on macOS 27.2.1 as under ipswrun ([native.txt](examples/expected/handlers/native.txt)), and the release's own zsh runs a `trap`.

What is not as a Mac has it:

- **A signal is taken when a thread comes back from the kernel,** from a system call or a trap, and by no thread that does not: nothing takes a thread off the CPU (limit 7), so a handler for a thread that spins waits with it.
- **A thread that waits for a lock, a Mach message or work** (`pthread_mutex_lock`, `mach_msg`, a parked thread of the work queue) is not brought back for a signal: it takes it when it comes back in its own time. A Mac's kernel interrupts some of these.
- **A fault is a signal to the thread that made it,** as a Mac's kernel makes of one: SIGSEGV for memory that is not there, SIGBUS for memory that may not be touched that way, SIGTRAP for a trap instruction, with where in what the handler is told and in its context. A handler that mends the cause returns to the instruction, which is made again. With no handler the process ends by the signal, and for the guest itself ipswrun says what the fault was and where, with its exit status 128 and the signal's number where it was 70. [examples/faults.c](examples/faults.c) prints the same natively as under ipswrun. An instruction the emulated CPU does not know still stops the run and is no SIGILL: it may be the emulator's lack and not the guest's fault (AMX, limit 4). What the chip says of the exception in the context (`esr`) is left out for a fault.
- **`setitimer` and `alarm`** send SIGALRM when their time is up, by the machine's clock, once or at every interval, and `getitimer` reads what is left. The timers of a process's own time on the CPU are read as not running, and starting one stops as unimplemented.
- **A page that may no longer be read is not read.** After `mprotect` took reading away from a page that had been read, it went on being read, as the engine remembered that it could be.
- **What the context says of the machine beyond its registers** is what was measured on one Mac at a system call: the exception the thread last took is that call, and the state is said to hold no signed pointers, as dyld is told too. One bit a Mac15,9 has set in the saved flags (0x1000) is left out, as it is the chip's.
- **A signal to a group** (`kill` with no pid, for the sender's own, or with a group's number below zero) is one to each process in it, the sender too, and with signal 0 only asks whether there is anyone to send one to, as `zsh` asks of every program it starts. A group no process is in is ESRCH; one whose only processes have ended and are still to be waited for, or are another user's, is EPERM, as a Mac's kernel was measured to say of the first. A process is in its parent's group unless `posix_spawn` starts it into its own; [examples/groups.c](examples/groups.c) prints the same natively. A process that has ended is there to be sent a signal until its parent has waited for it or has ended too, as measured.
- **What stops the run as unimplemented:** the signals that stop a process, `kill` of every process (-1), a signal to launchd from root, and a `sigreturn` with a context the kernel did not make. `sigwait` waits for good. No thread is ever cancelled.

## A kqueue of the guest's own

`kqueue` and `kevent` (and `kevent64`) are there for what can happen here: an event the program makes happen itself (`EVFILT_USER`, with its flags set, masked and added to), timers, an end of a pipe that can be read or written, and a process ending. A note is taken once, or disabled when taken, or cleared, or returned as often as it is asked for, as it was added; a change is answered with a receipt or its error where there is room; a wait ends when its time is up or another thread or process makes something happen. [examples/kqueue.c](examples/kqueue.c) prints the same natively on macOS 27.2.1 as under ipswrun ([native.txt](examples/expected/kqueue/native.txt)). Thirteen of the release's programs made a kqueue of their own in the survey.

What is not there: a file (`EVFILT_VNODE`), a signal, a Mach port, a descriptor that is no pipe's, and the end of a pipe that is not the one read or written are accepted, as they were, and never happen; a `kevent` that would wait while one of those is watched stops as unimplemented, where it used to stop for any wait. `kevent_qos` on a kqueue with a descriptor still answers nothing.

A thread that starts a process now goes on before the process first runs, as a parent does on a Mac; it used to be the child that ran first.

## poll, and select of a file

`poll` answers for the ends of a pipe, for a file, which can always be read and written, for a directory and a descriptor that is not open, which it calls invalid, and waits for a pipe as long as it is told to, or until a signal. [examples/poll.c](examples/poll.c) prints the same natively on macOS 27.2.1 as under ipswrun ([native.txt](examples/expected/poll/native.txt)); it differs from `select` in what it says of the end of a pipe that is not the one asked about, as a Mac's does. `select` now says of a file what a Mac's says, that it can be read and written, where it found nothing ready. A `poll` that would wait for a terminal or a kqueue stops as unimplemented.

## A port's status

`mach_port_get_attributes` answers a receive right's status and its queue's limit as macOS 27.2.1 does: [examples/portstatus.c](examples/portstatus.c) prints the same natively on a Mac as under ipswrun ([native.txt](examples/expected/portstatus/native.txt)), through messages sent and received, rights to send once made, used, given up and kept by the kernel for a notification, limits, sets and guards. For it the kernel here now keeps, of every port, the rights to send once that exist for it, how many messages were received from it (which a message's trailer says too: it said 0), the limit of its queue, and its guard. A reply now arrives through the right it was given to answer with, where it used to arrive as if through a right to send once whatever it was given.

What is not known for sure stops as unimplemented: the other flavors (the owner, importance, the guard's own info, throttling), and the status of a name that is no port's here, which may be a name that is gone (an invalid name to a Mac) or a right the kernel keeps of another kind, such as a thread's (an invalid right). Not checked against a Mac: unguarding a port with a value that is not its guard, for which a Mac's kernel ends the process, also stops as unimplemented. The limit of a queue is kept and read back, and holds no sender to it. `mach_port_type` still answers that every name is a send right.

## Sysctls left out

A sysctl whose value is not known for sure for the release and device is not answered (ENOENT), rather than answered with another chip's or release's value:

- `hw.cpufamily` of a device not in `cpuFamilies`: of the Macs, only those with an M1, M1 Pro, Max or Ultra are there. The commpage's family is then 0 too.
- `hw.l1icachesize`, `hw.l1dcachesize` and `hw.l2cachesize`, except on an M1 Mac: an iPhone's or iPad's chip has its own.
- `hw.cpusubfamily` and the `hw.perflevel0` fields other than its core counts (`name`, `l2cachesize`, `cpusperl2`, `physicalcpu_max`), which libBLAS asks for and does without.
- `kern.version`, which names the build's kernel and when it was built; `kern.iossupportversion`, which is a Mac release's own (in its `SystemVersion.plist`); `kern.osproductversioncompat`, which a Mac of macOS 27 leaves empty; `kern.maxfilesperproc`, which follows the device's memory.
- `kern.boottime` and `kern.bootsessionuuid` are answered, as the machine's own ([above](#what-logd-asked-for)).
- `hw.cpubrand`, which no kernel has (a Mac's brand is `machdep.cpu.brand_string`).

What describes the emulated machine itself stays: one CPU (`hw.ncpu` and the `perflevel0` counts), 8 GB, half of it free (`kern.memorystatus_level`).

## AMX emulation

Apple's matrix coprocessor is reached by instructions in an encoding Arm leaves undefined (`0x00201000`, an operation in bits 5–9 and a register in bits 0–4): set and clear, loads and stores of its X, Y and Z registers, extracts, and the multiply-accumulate, vector and matrix operations in 16-, 32- and 64-bit floating point and integers. Reverse-engineered descriptions of all of them are public. Emulating them in Go, from the hook that now stops the run, would let Accelerate run: a register file per thread, kept across context switches, and each instruction checked against the host's own results on an Apple silicon Mac. Every AMX instruction would leave Unicorn for Go, so it would be correct but slow.

## Out of reach under the current rules

Each of these needs a kernel driver, so with no kext emulation they stay out. Offscreen work that is pure CPU should still run.

- **GUI.** AppKit's `NSApplication` needs WindowServer, and WindowServer needs the framebuffer, IOSurface and GPU drivers. UIKit needs SpringBoard and backboardd on top of that. CoreGraphics bitmap contexts and ImageIO should work. CoreText also needs `/System/Library/Fonts` opened with `--system`, and probably fontd.
- **Metal and the GPU.** With no GPU driver, `MTLCreateSystemDefaultDevice` returns nil. CoreImage and CoreML fall back to CPU paths where they have them, and anything built on IOSurface fails.
- **Keychain and data protection.** The data-protection keychain sits on AppleKeyStore. Only non-permanent, iOS-style keys work today, as the readme says.
- **Sandbox, AMFI and TCC enforcement.** Nothing is checked, so sandbox profiles and privacy prompts can't be observed. tccd could run as a daemon, but most of what it guards leads to more drivers.
- **macOS before 11.** Those releases have no arm64 code.

## Suspicions not yet tested

These come from reading the code and are the ones most worth a run on a Mac.

- **JavaScriptCore's JIT.** `MAP_JIT` and `pthread_jit_write_protect_np` use system registers that only Apple's cores have, which is probably an undefined instruction here. `JSC_useJIT=0` should still run JavaScriptCore as an interpreter.
- **SQLite WAL and Core Data.** Core Data opens WAL stores and may hold two connections to one. With `-shm` mapped privately, each connection sees its own copy.
- **os_log output.** Without logd, logs go nowhere; with it ([above](#daemons-on-demand)) they are in its files, which nothing here reads back. `os_log_type_enabled` says debug messages are logged, with logd or without, where a Mac says they are not; why was not looked for. `--env OS_ACTIVITY_DT_MODE=1` may copy them to standard error, which would help when debugging daemons.
- **Speed.** Only one guest thread runs at a time, on one host core. A CPU-bound benchmark, such as 10 MB through CommonCrypto's SHA-256, would put a number on the slowdown against native.
